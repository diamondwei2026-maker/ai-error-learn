# 本项目开发工作流全局规则

## 1. 文档体系规范

- 主系统基线 spec 路径：.trae/specs/main-system/
- 增量文档目录：.trae/docs/increments/
- 全局变更索引：.trae/docs/change-log.md
- 原型根目录：.trae/prototypes/（新项目完整原型）
- 增量原型目录：.trae/docs/increments/[增量文件夹]/prototype/
- 所有文档、原型文件必须按上述路径存放，禁止乱放

## 2. 原型工作流强制规则

> 页面类前端需求，必须执行双阶段原型流程，**严禁跳过原型直接进入编码**

1. 阶段1：使用 frontend-design 生成纯HTML+CSS骨架原型
   - 只关注信息架构、页面布局、模块位置、交互流转，不做精细视觉美化
   - 生成后暂停，等待用户确认结构；结构未确认，**禁止进入视觉优化**
2. 用户确认结构后，阶段2：使用 ui-ux-pro-max 基于已确认骨架做视觉优化
   - 新项目：统一设计规范；增量需求：严格对齐项目现有UI设计语言
   - 生成高保真纯HTML+CSS原型，暂停等待用户确认视觉；视觉未确认，**禁止进入正式代码开发**
3. 原型产物分为 skeleton（骨架）、visual（高保真视觉）两个子目录分开存放
4. 增量需求：仅制作新增/修改模块的原型，不需要重绘整个页面；原型需要体现和原有页面的上下文关系

## 2.1 原型内容纯净度强制规范

> 核心原则：**原型页面内只出现真实用户可见的元素和文案，所有设计说明、逻辑注释、开发提示一律不得侵入界面**

1. 禁止在页面内部写入任何非用户可见内容，包括但不限于：
   - 逻辑说明：如“启动已静默登录 → 此处仅需授权头像昵称”
   - 规则注释：如“原图仅保存在本设备；换设备后可刷题，但无原图”
   - 开发提示：如“微信头像选择能力 chooseAvatar”
   - 状态标注：如“新增”“未登录·仅本地”等括号内说明文字
2. 界面内的占位文案必须是真实产品文案的模拟：
   - 按钮只写按钮文字（如“微信一键登录”“保存”），不加后续解释
   - 状态只展示用户看到的最终文字（如“未登录”“已同步”），不加括号备注
   - 头像、昵称区域只用视觉占位，不写开发能力说明
3. 所有设计说明、状态差异、逻辑备注，统一放在原型页面**下方单独的「设计说明」区块**，或者写入配套的说明文档，绝对不允许出现在界面框架内
4. 多状态原型可以并排展示多个页面，每个页面只展示该状态下的真实界面；状态差异说明放在页面组的下方，不侵入单个页面

## 2.2 原型调研与同类产品参考规范

1. 所有页面类原型生成前，必须先联网调研同赛道、同类型的主流产品，参考行业通用设计模式与交互习惯，避免反常识设计。
2. 分阶段参考重点：
   - 骨架阶段（frontend-design）：重点参考**信息架构、模块划分、页面布局、核心交互流程、功能入口设计**
   - 视觉阶段（ui-ux-pro-max）：重点参考**主流设计风格、组件样式规范、配色体系、排版层级、细节质感**
3. 调研输出要求：
   - 生成原型前，先输出 3-5 条核心参考总结，说明主要借鉴的设计点
   - 所有调研思路、设计决策说明、参考来源，统一写入原型下方的「设计说明」区块，**严禁侵入界面内容**
4. 增量需求场景：仅针对本次新增/修改的功能模块做定向调研，无需全产品调研；最终设计必须优先对齐现有产品的整体设计体系，不能照搬参考产品的风格。
5. 若用户指定了具体参考产品，优先按指定产品调研；未指定则调研行业排名前三的主流同类产品。

## 3. 增量开发默认规则

- 普通轻量增量：使用 /plan，文档存入 increments 目录，**禁止直接修改主 spec**
- 高风险增量（核心链路、数据模型、跨模块）：使用 /spec，独立归档
- 每次增量开发完成，必须自动更新 change-log.md，追加变更记录
- change-log 必须包含：编号、日期、变更摘要、影响模块、关联文档路径、是否待合并主spec

## 4. 开发默认行为

- 所有开发任务：先输出计划/方案，**禁止直接写代码**，等用户确认后再执行
- 涉及修改现有代码：必须先说明影响范围和改动文件清单
- 每个任务完成后，自动输出变更摘要
- 默认遵循项目现有代码风格、命名规范、架构模式

## 5. 需求变更规则

- 优先采用兼容层方案，保留旧逻辑，支持回滚
- 分步执行，关键节点自动暂停等待验证
- 大型变更必须提供灰度切换方案

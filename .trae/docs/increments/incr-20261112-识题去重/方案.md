## 一、问题背景

### 1.1 现状诊断

当前识题→入库链路完全没有题目去重能力：

- **识题接口** `recognize.py`：只做 OCR + VLM 拆题（题干 + 解答），返回即结束
- **数据模型** `question_sync.py`：以 `(user_id, item_id)` 为唯一约束，`item_id` 是客户端生成的时间戳+随机串，数据库**完全不感知题目内容**
- **前端保存** `questionService.ts`：`create()` 直接生成新 ID → 存图片 → 写列表 → 返回，零查重

用户对同一道题拍两次照，会得到两条完全独立的错题记录，各自有独立的复习排期、独立的统计计数。

### 1.2 三类"重复"场景

| 场景 | 性质 | 应该怎么做 |
|------|------|-----------|
| A. 同一道题，同一考试中两次独立犯错 | 真实需求，不是重复 | **该保留**（两道独立错题） |
| B. 同一道题，想存多种解法对照 | 后期"一题多解"笔记功能 | **MVP 不做** |
| C. 同一道题，纯粹手滑拍了两次 | 无意产生的冗余 | **本方案要解决的** |

### 1.3 跨用户去重

**个人错题本场景下不存在此问题**——数据库按 `user_id` 隔离，不同用户的错题完全独立。跨用户共享题库是远期公共题库的事，MVP 不碰。

## 二、目标与范围

### 2.1 目标

在不阻塞正常录入、不误杀真实需求的前提下，识别并提醒用户避免重复录入同一道错题。

### 2.2 设计原则

1. **温和提醒，不强制拦截**——用户确认后仍可保存（可能是场景 A 或 B）
2. **精确匹配优先**——MVP 只做完全相同题干的精确哈希匹配，不做语义相似度
3. **客户端本地检测**——不上到服务端，零额外网络请求
4. **零误杀**——精确哈希只在文本完全一致时命中，不把用户真的想存的题当成重复

### 2.3 明确不做

- ❌ SimHash / MinHash / 向量 embedding 等语义匹配（讯飞专利明确 SimHash 对短文本效果差，向量索引对 MVP 量级杀鸡用牛刀）
- ❌ 自动合并重复题目（误杀代价远大于保留重复的代价）
- ❌ 跨用户去重（个人错题本数据天然隔离）
- ❌ 一题多解关联模型（后期真实用户反馈驱动再做）

## 三、技术方案

### 3.1 核心思路

给题干做**标准化 → SHA-256 哈希**，存入题目记录。每次创建新题前，对标准化后的题干算哈希，比对本地已有题目的哈希表。命中则弹温和提醒。

### 3.2 为什么选 SHA-256 而不是其他

| 方案 | 优点 | 缺点 | 适用性 |
|------|------|------|--------|
| **SHA-256（精确匹配）** | 计算极快、碰撞概率≈0、标准库自带 | 只认完全相同的文本 | ✅ 适合 MVP |
| SimHash | 支持近似匹配 | 对短文本（单道题通常几十字）区分度差 | ❌ 讯飞专利已证 |
| MinHash + LSH | 规模化相似去重 | 实现复杂、仍属近似匹配 | ❌ 杀鸡用牛刀 |
| Embedding + HNSW | 语义匹配最强 | 需要向量数据库、算力成本高、误杀风险大 | ❌ 等题量 > 500 再考虑 |

### 3.3 标准化逻辑（哈希前的文本预处理）

OCR 对同一张图可能有细微差异（全角/半角、换行数、空白等），标准化确保这些差异被抹平：

```
normalizeForHash(text):
  1. unicodedata.normalize('NFKC', text)   # 全角→半角
  2. re.sub(r'[^\S\n]+', ' ', text)        # 所有空白→单空格（保留换行）
  3. re.sub(r'\n{3,}', '\n\n', text)       # 3+ 换行→2 个
  4. return text.strip()                   # 去首尾空白
```

注意：**不做数学公式符号的语义等价处理**（如 `×` vs `*` vs `x`）。这类情况属于语义相似度范畴，MVP 阶段不覆盖。

### 3.4 去重检查流程

```
用户拍照/选图
    ↓
识题接口 → 返回题干（content）
    ↓
客户端：标准化 + SHA-256 → contentHash
    ↓
遍历本地 questionStore → 比对已有题目的 contentHash
    ↓
├─ 命中 ≥ 1 条：
│   弹温和提醒 Modal：
│   标题：「这道题好像已经记录过了」
│   内容：展示已录入题目的题干预览 + 创建时间
│   按钮：[查看已录入]  [仍然保存]  [取消]
│
└─ 0 条命中：
    正常进入编辑页 / 直接保存
```

### 3.5 提醒弹窗文案与交互

```
┌─────────────────────────────────────┐
│  ⚠️  这道题好像已经记录过了           │
├─────────────────────────────────────┤
│  你之前在 2026-11-10 录入过：         │
│  "已知函数 f(x) = x² + 2x - 3，      │
│   求 f(x) 的最小值..."               │
│                                     │
│  确定要再存一次吗？                   │
├─────────────────────────────────────┤
│  [查看已录入]    [仍然保存]    [取消] │
└─────────────────────────────────────┘
```

按钮行为：
- **查看已录入**：跳转到题库详情页该题的位置
- **仍然保存**（强调色按钮）：跳过检查，正常保存
- **取消**：返回上一页（不保存、不进入编辑）

## 四、数据模型变更

### 4.1 客户端 `Question` 类型扩展

```typescript
// client/src/types/question.ts
export interface Question {
  // ... 现有字段保持不变 ...
  contentHash?: string   // 标准化题干的 SHA-256（64 字符），去重用

```

`contentHash` 设为可选（`?`），兼容存量题目（存量没有该字段，会被排除在去重比对之外）。

## 六、风险清单

| 编号 | 风险 | 影响 | 应对 |
|------|------|------|------|
| R1 | 存量题目无 `contentHash`，去重对存量失效 | 老用户重复录入时无提醒 | 启动时批量回填：对存量题目的 content 算标准化哈希 |

## 八、验证方案

| 维度 | 方法 |
|------|------|
| 哈希正确性 | 单元测试：相同文本多次计算 → 哈希一致；不同文本 → 哈希不同；OCR 细微差异（全角/半角、空白）→ 标准化后哈希一致 |
| 去重逻辑 | 手工测试：同一题干录两次 → 第二次弹提醒；不同题干 → 无提醒 |
| 存量兼容 | 旧 Storage 数据读取 → 无报错；存量题能正常回填哈希 |
| 同步兼容 | 登录态下新建带 `contentHash` 的题 → 云端可见；换设备拉取 → 哈希一致 |
| 迁移安全 | 对现有 `server/app.db` 启动一次 → 补列；连续启动 → 不报错 |

| 阶段 | 触发条件 | 方案 |

设计说明 · 阶段1 骨架

阶段1本页只表达信息架构 / 布局 / 模块位置 / 交互流转，不做视觉美化。配色仅借用现有设计令牌，用于体现「与现有系统的一致性」。界面内文案均为真实用户可见文案的模拟，所有设计说明统一放在本区块。

一、同类产品定向调研参考点（3~5 条）

  1. 弹层形态用「底部弹层」而非居中弹窗：微信生态内隐私/授权类二次确认普遍采用底部弹层，与现有 LoginSheet、ActionSheet 一致，避免新增视觉体系。
  2. 「同意」必须是原生按钮，且必须提供「拒绝」路径：微信要求自定义弹层中的同意按钮须为 <button open-type="agreePrivacyAuthorization">，且不得默认勾选、不得只留「同意」一条路。
  3. 弹层内必须提供「查看平台隐私协议」入口：微信要求弹窗须能跳转 wx.openPrivacyContract，否则不合规。
  4. 采用「启动非阻断」而非「强制同意才能进入」：违规点是「不同意就退出/拒绝后不提供服务」，本产品已有游客模式（首页/题库/刷题免登录），因此弹层提供「暂不授权」，拒绝后主流程照常可用。
  5. 协议页用「长文分段 + 小标题 + 更新日期」的通用信息架构：主流小程序的协议页均为单页长文、可返回、无底部操作栏，不引入富文本/markdown 依赖。

二、结构要点

模块位置结构说明
隐私弹层 PrivacySheet底部弹层（复用 LoginSheet 面板规范）标题 → 正文（含《用户协议》《隐私政策》可点链接）→「查看平台隐私协议」→ 主按钮「同意并继续」→ 文字按钮「暂不授权」
弹层挂载点6 个页面根节点末尾小程序 App 组件不渲染页面节点，弹层须逐页挂载
协议页 agreement新增页面，query 区分类型NavBar(showBack) + 更新日期 + 分段小标题正文；?type=privacy / ?type=terms 共用一套结构
「我的」页入口用户卡 → 操作列表 之下新增「服务协议」区块：用户协议 / 隐私政策 两行；未登录也显示，复用现有 .row 样式

三、触发时机（已确认：启动非阻断）

  • 启动时：查询授权状态，若需授权则弹本弹层（图 1a）。用户可「同意并继续」，也可「暂不授权」。
  • 暂不授权后：首页 / 题库 / 刷题照常可用；仅拍照识别、更换头像、填写昵称等隐私功能不可用（点击时再次引导，见图 1b）。
  • 兜底：任意隐私接口被调用时，弹同一个弹层，保证「同意 / 拒绝」两条分支都能继续。

四、明确不做（边界）

  • 不做「不同意就退出小程序 / 拒绝后中断全部服务」的强制形态。
  • 不改动任何业务逻辑、数据模型、识别与同步链路。
  • 不引入 markdown / 富文本依赖（协议页用纯文本分段排版）。

五、待确认事项

  • 弹层正文文案与协议正文口径需一致，最终文本须与微信后台《用户隐私保护指引》声明保持一致。
  • 协议正文的完整文本将在编码阶段按「隐私政策要点 / 用户协议要点」起草，上线前需你确认（尤其第三方 AI 处理披露与联系方式）。

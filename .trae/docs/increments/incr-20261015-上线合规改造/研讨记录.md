## 2. 联网调研结论（本次定向调研）

调研对象：微信官方《小程序隐私协议开发指南》《收集用户隐私行为规范与修改指引》，以及社区同类问题。

| # | 结论 | 对设计的影响 |
| --- | --- | --- |
| R1 | 官方 demo1 **确实在首页 onLoad** 用 `getPrivacySetting` 判 `needAuthorization` 后弹窗 → 「启动弹窗」本身不违规 | 启动弹层方案可行 |
| R2 | 违规点是**阻断**：「不同意就不能进小程序」「拒绝后不提供服务」属违规 | 弹层必须提供「暂不授权」，拒绝后主流程照常可用 |
| R3 | 《收集用户隐私行为规范》：用户**未触发相关功能就要求授权**属违规收集 | 启动弹层存在边缘风险，需以「非阻断 + 已有游客模式」化解 |
| R4 | 自定义弹层中「同意」须为 `<button open-type="agreePrivacyAuthorization">`；不得默认勾选、不得只留同意 | 弹层按钮形态确定 |
| R5 | 弹层必须能跳转 `wx.openPrivacyContract`（平台隐私协议） | 弹层内固定一条「查看平台隐私协议」入口 |
| R6 | `<input type="nickname">` 未同意时**不触发** `onNeedPrivacyAuthorization`，会静默降级为普通文本输入 | 昵称输入聚焦时须**主动**触发授权 |
| R7 | `Taro.login()` **不是**隐私接口（不在声明清单内），真正的隐私调用点只有 3 个 | 授权范围收窄：`chooseMedia` / `chooseAvatar` / `input type="nickname"` |

### 核实到的隐私调用点（全仓）

| --- | --- |
| `Taro.chooseMedia` | `client/src/services/captureService.ts` |

## 3. 关键决策

| 决策项 | 结论 | 理由 |
| --- | --- | --- |
| **隐私授权触发时机** | **启动非阻断弹层**（用户已确认） | 对齐官方 demo1；弹层提供「暂不授权」，拒绝后首页/题库/刷题照常可用（已有游客模式），规避「阻断」违规形态 |
| 弹层形态 | 底部弹层，复用 `LoginSheet` 面板规范 | 与现有「同意类」交互一致，不新增视觉体系 |
| 协议页形态 | 隐私政策 + 用户协议**合并为 1 个页面**，query 区分 | 两页结构同构，避免重复代码 |
| 「我的」页入口位置 | 用户卡 → 操作列表 之下，新增「服务协议」区块 | 未登录也显示，复用现有 `.row` 样式 |
| 协议正文渲染 | 纯文本分段（`<Text>`） | 不引入 markdown / 富文本依赖 |

## 4. 与上级方案的差异（需并入上级方案）

上级方案 M1 §3.1 为「**主动弹 + 被动兜底**」，其中「小程序启动即弹」表述过于绝对。本次修正为：

- 启动弹层**必须非阻断**：提供「暂不授权」，拒绝后不得中断任何非隐私功能。
- 被动兜底保留：任意隐私接口被调用时弹同一弹层，并保证同意/拒绝两条分支都能 `resolve`。
- 昵称输入聚焦时主动触发（R6）。

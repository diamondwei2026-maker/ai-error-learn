# 识别失败报错修复方案（recognize 服务）

## 1. Summary

定位并修复拍照识别固定报错「识别失败，请重试或手动输入」。

已完成的实测结论：

- 本地 `server/.env` 的 GLM-4V-Flash 配置**可用**：直连 `https://open.bigmodel.cn/api/paas/v4/chat/completions` 返回 200（1×1 PNG、215KB 真实照片、5MB 带填充图片均成功，耗时约 3–4 秒）；`VisionClient.recognize()` 同参数直调也正常返回。
- 「识别失败，请重试或手动输入」这句话在全仓库**只有一处来源**：[vision_recognize.py](file:///d:/Users/weij/ai-error-learn/server/app/services/vision_recognize.py#L102-L120) 的 `_map_to_error` 兜底分支。即请求已到达后端，是**上游多模态模型调用返回了非 200 且未被现有规则识别**。
- 生产部署模板与部署教程把模型配成百炼的 `VISION_MODEL=qwen-vl-flash`，但百炼当前多模态模型 ID 为 `qwen3-vl-flash` / `qwen-vl-plus` / `qwen-vl-max` 等，**不存在 `qwen-vl-flash`**；上游会返回参数/模型不存在错误，被 `_map_to_error` 归入通用 1002 → 每次必现。
- 本地当前 8000 端口未监听（后端未启动），本地联调若未先 `npm run server`，也会表现为识别失败（前端兜底文案）。

因此本次修复分两层：**A. 纠正错误配置 + 按状态码细分错误文案（实际修复）**；**B. 补上游日志与客户端日志（根因可见、防复发）**。

## 3. Proposed Changes

### 3.1 后端：错误映射细分 + 上游日志（`server/app/services/vision_recognize.py`）

- 新增模块级 `logger = logging.getLogger(__name__)`。
- `_map_to_error` 调整判定顺序与文案（保持 429→1003、401/403→1005 不变）：

  | 触发条件 | 错误码 | 文案 |
  | --- | --- | --- |
  | 429 / quota 关键字 | 1003 | 识别额度受限，请稍后再试 |
  | 401 / 403 / auth 关键字 | 1005 | 识别服务未开通或无权限，请检查密钥配置 |
  | **400 / 404 / 422** | **1005** | **识别模型不可用，请检查 VISION_MODEL 配置** |
  | **5xx** | 1002 | 识别服务暂时不可用，请稍后重试 |
  | **`httpx.TimeoutException`** | 1002 | 识别超时，请重试 |
  | **网络/连接异常** | 1002 | 识别服务连接失败，请检查网络 |
  | 其它 | 1002 | 识别失败，请重试或手动输入 |

- 在 `VisionClient.recognize` 内：
  - `except Exception` 捕获到网络/超时异常时，`logger.warning("vision upstream exception: %s: %s", type(exc).__name__, exc)`。
  - `response.status_code != 200` 时，`logger.warning("vision upstream non-200: status=%s body=%s", response.status_code, response.text[:300])`，再调用 `_map_to_error`。
  - 日志只记录状态码与响应体截断，绝不打印 `Authorization` / API Key。

### 3.2 后端：启动期配置告警（`server/app/main.py`）

- 在现有 `jwt_secret` / `wechat_app_secret` 告警旁新增：
  - `settings.vision_enabled and not settings.vision_configured` → warning：`视觉模型已开启但未配置 VISION_API_KEY / VISION_BASE_URL，识别将返回 1002`。
  - `settings.vision_configured` → info：`视觉模型：base=<host> model=<model> timeout=<n>s`（不打印 key）。

### 3.4 前端：区分网络失败与识别失败（`client/src/services/recognitionService.ts`）

- 后端返回非 0 时：`console.warn('[recognitionService] business failure', { statusCode: res.statusCode, body })`（body 仅含业务字段，不含 token）。
- `catch` 分支：`console.error('[recognitionService] upload failed', error)`，文案改为「识别服务连接失败，请检查网络或稍后重试」；页面仍进入「识别失败 · 请手动输入」态，不影响手动录入。
- 不改动 `uploadFile` 的 30s 超时（后端上游 20s，实测 3–4s，留足余量）。

### 3.5 测试（`server/tests/test_vision_recognize.py`）

- 500 → `CODE_RECOGNIZE_FAILED`，`message` 为「识别服务暂时不可用，请稍后重试」。
- `httpx.ReadTimeout` → `CODE_RECOGNIZE_FAILED`，`message` 为「识别超时，请重试」。
- 现有 401/403/429/网络异常用例断言保持通过。

## 4. Assumptions & Decisions

1. 生产按部署教程使用了百炼 `qwen-vl-flash`（推断）。若实际用的是 GLM 或其它模型，3.1 的日志会直接打印上游 status/响应体，一次复现即可定位。
2. 不新增 1006 错误码：后端 `message` 已优先展示，复用 1005/1002 + 明确文案改动最小；前端错误码字典无需变动。
3. 不做自动重试/多模型降级：避免掩盖根因、增加额度消耗；先保证错误可诊断。
4. 本次为后端错误处理与配置修正，无页面结构调整，**不触发双阶段原型流程**。
5. 本地失败按“后端未启动”处理：验证步骤先启动 `npm run server`；若启动后仍失败，日志可立即定位。

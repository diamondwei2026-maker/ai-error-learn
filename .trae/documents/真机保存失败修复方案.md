# 真机保存失败修复方案（识别成功 → 保存入库提示「保存失败」）

> 日期：2026-11-12 ｜ 类型：缺陷修复（轻量） ｜ 关联增量：`incr-20261112-识题去重`

---

## 一、问题现象

真机调试路径：拍照/选图 → 识别题目成功（看到题干与答案）→ 点「保存入库」→ Toast 提示 **「保存失败，请重试」**，题目未入库。

开发者工具模拟器同一路径表现正常（或至少不发生该报错）。

## 二、根因定位（已完成代码级确认）

### 2.1 失败链路

[编辑页保存](file:///d:/Users/weij/ai-error-learn/client/src/pages/edit/index.tsx#L117-L175) → `handleSave` → `questionService.create()` → [create 第 62 行](file:///d:/Users/weij/ai-error-learn/client/src/services/questionService.ts#L62) 调用 `computeContentHash()` → 抛异常 → 被 `handleSave` 的 `catch` 兜住 → 弹「保存失败，请重试」。

### 2.2 抛异常的具体位置

[textHash.ts](file:///d:/Users/weij/ai-error-learn/client/src/utils/textHash.ts#L20-L31) 使用了 **Web 平台 API**：

```ts
const encoder = new TextEncoder();
const data = encoder.encode(normalized);
const hashBuffer = await crypto.subtle.digest("SHA-256", data);
```

- 微信小程序运行时（真机 iOS JSC / Android V8 小程序环境）**不提供 `TextEncoder`，也不提供 `crypto.subtle`**，执行到此处直接抛 `TextEncoder is not defined` / `crypto is not defined`。
- 微信开发者工具模拟器运行在 Chromium 环境，这两个 API 存在，因此**模拟器正常、真机必现**，与本次现象完全吻合。

### 2.3 构建产物证据

`client/dist/common.js` 中该函数未被任何 polyfill 替换，仍为原始调用：

```js
a=new TextEncoder,c=a.encode(n),e.n=2,crypto.subtle.digest("SHA-256",c)
```

`client/config/index.ts` 未配置任何 `TextEncoder` / WebCrypto polyfill，`@tarojs/plugin-html` 也不提供该能力。

### 2.4 为什么只有「保存」这一处暴露

| 调用点 | 是否有 try/catch | 表现 |
| --- | --- | --- |
| [edit 页去重检查](file:///d:/Users/weij/ai-error-learn/client/src/pages/edit/index.tsx#L123-L137) | 有（降级放行） | 去重功能在真机静默失效，不报错 |
| [App 启动回填](file:///d:/Users/weij/ai-error-learn/client/src/app.tsx#L24-L34) | 有（仅日志） | 真机静默失败 |
| [questionService.create](file:///d:/Users/weij/ai-error-learn/client/src/services/questionService.ts#L49-L90) | **无** | 直接抛错 → 整个本地保存失败 |

即：`incr-20261112-识题去重` 引入的 WebCrypto 依赖，使「去重」这一**辅助能力**成了「保存」这一**主链路**的硬依赖，且该依赖在真机运行时不存在。

### 2.5 已排除的其它可能

- 网络：识别上传成功，说明 `API_BASE` 在真机可达；且保存前的内容安全预检失败会降级放行，不阻塞保存。
- 本地文件：`Taro.env.USER_DATA_PATH` 在 Taro 4.1.9 类型中存在，`copyFileSync` 走标准路径，非本次失败点。
- Storage 容量：单题记录仅数百字节，与「每次保存必失败」的现象不符。

## 三、修复方案

### 3.1 核心改动：用纯 JS 实现 SHA-256，去掉 Web API 依赖

**文件**：`client/src/utils/textHash.ts`（重写内部实现，对外导出与签名保持不变）

- `normalizeForHash(text)`：
  - 保留现有 NFKC + 空白/换行归一逻辑；
  - `String.prototype.normalize` 加存在性判断与 try/catch，异常时退化为原文（老设备兜底）。
- 新增内部 `utf8Encode(str): Uint8Array`：
  - 手写 UTF-8 编码（含代理对处理），替代 `TextEncoder`。
- 新增内部 `sha256Hex(str): string`：
  - 纯 JS SHA-256（标准 64 常量表 + `Math.imul`），返回 64 位小写 hex，**与原 WebCrypto 结果逐位一致**，存量 `contentHash` 继续可匹配。
- `computeContentHash(text)`：保持 `async` 签名，内部改为 `return sha256Hex(normalized)`，调用方零改动。

> 不引入任何第三方依赖（避免增加小程序包体与新的运行时兼容风险）。

### 3.2 加固：辅助能力不得阻断主链路

**文件**：`client/src/services/questionService.ts` → `create()`

- 将 `computeContentHash` 调用包进 try/catch：
  - 成功：写入 `contentHash`；
  - 失败：`console.error` 记录，`contentHash` 置 `undefined`，**继续完成图片落盘与入库**。
- 理由：去重是辅助能力，任何哈希异常都不应让用户无法保存错题（与 edit 页现有降级策略保持同一口径）。

### 3.3 不改动项

- `edit/index.tsx` 的交互与文案（「保存失败，请重试」保留，用于真正的存储异常）。
- `syncService` / 服务端 `content_hash` 字段与同步协议（哈希值算法不变）。
- `backfillContentHash` 逻辑（修复后自动生效）。

## 五、风险与回滚

| 风险 | 应对 |
| --- | --- |
| 纯 JS SHA-256 与标准实现不一致，导致新旧哈希对不上 | 用 Node `crypto` 做逐用例比对（中英文/含 emoji/全角/多行/200 字长度），必须完全相等 |
| 纯 JS 实现性能 | 题干上限 200 字，单次耗时微秒级，可忽略 |
| 改坏标准化逻辑，导致去重误判 | `normalizeForHash` 逻辑保持原样，仅加环境兜底 |

**回滚方式**：`git revert` 本次提交即可；`contentHash` 字段为可空字段，回滚不影响已存数据读取。
